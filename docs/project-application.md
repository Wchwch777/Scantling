# Scantling Trace：MQTT 有状态协议轨迹校验器（十一月申报书）

**参赛者：** 韦昌豪 / Wchwch777　**申报方向：** 新生态项目建设（新组件范围以赛事组认定为准）
**仓库：** https://github.com/Wchwch777/Scantling　**类型：** 原创工具，非移植　**许可证：** Apache-2.0

## 问题与定位
十月申报未通过初审，评审指出脚本对端主要是逐包匹配与线性收发、独立协议语义不足。我认可这一判断，十一月不再以客户端或线性脚本申报，改为补上生态缺少的一层：独立观察双向历史的校验器。能解码的 ACK 也可能不属于当前 QoS 阶段；两端可以同时使用同一 id，单方却不能在未完成时复用它；重传必须 DUP=1 且内容一致。判定这些历史关系需要完整轨迹与阶段状态，单包解码或线性匹配都给不出。

## 本期新增（基线 `1e63972`，不重复计入旧客户端、编解码与线性脚本）
- `mqtt/monitor` 纯计算包：按 `(发送端, packet identifier)` 建在途事务表，驱动 QoS 1/2 四步握手、订退阅应答与重传一致性；同一连接允许多事务交错；报告给出事件位置、违反的规范条款与原因，并区分「协议违规」与「仅未完成前缀」；含 Clean Session 清理、已知持久会话恢复与逻辑时钟 Keep Alive 检查；首错冻结、报告脱离内部容器、每方向在途上限可配。
- `examples/check_trace` CLI 与五类参考轨迹：文本轨迹重放，语法错误报行号、语义违规报事件号，每类轨迹给出可复现的退出码与 JSON。
- 监控对端与真实 TCP 集成测试：脚本对端可选监控模式，同时观察客户端输入与服务端输出，把错误 ACK 归因到对端而非被测客户端；含总时限保护与异常清理。
- 编解码复用 `zbhzs1/moonbit-mqtt`，网络复用 `moonbitlang/async`；状态关联与诊断为本次实现。

## 三个完整使用场景
1. 客户端库回归：一份轨迹同时放入双向同 id 的 QoS 2 与交错 QoS 1，各自完成握手（`interleaved`：14 事件、3 笔完成、退出 0）；把某步 PUBREC 换成 PUBACK 后，CLI 在对应事件报 `TRACE-ACK-STAGE` 并以退出 1 失败。
2. 故障定位与 CI 门禁：任意轨迹交给 CLI 输出 JSON，违规或缺终态均非零退出；`keepalive-overdue` 用逻辑时间在 3001ms 报 `MQTT-3.1.2-24`，无须真实等待；`incomplete` 只报未完成（`valid_prefix=true`），不夸大为协议违规。
3. 断线恢复校验：`persistent-resume` 重放持久会话在 PUBREL 后断线、恢复后继续完成，核对 2 连接、1 笔完成、1 次重传、无重复计数；在线模式用独立 `mosquitto_pub/sub` 客户端交叉验证，不把测试对端的错误归给被测客户端。
